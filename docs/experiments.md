# Experiments: prompt v1 vs v2

Four runs: two local models (Llama 3.1 8B and Qwen 2.5 7B via Ollama 0.40.17, temperature 0, context window 4096 tokens) × two prompt versions, scored on the same 26 hand-labelled postings (15 English, 8 German, 3 French). All tables were generated by `python -m extractor.evaluate` and `python -m extractor.compare`. The full per-field, per-language tables are in [outputs/comparison.md](../outputs/comparison.md).

## 1. The measuring stick, fixed before the experiments

### Metric version 2

Scoring rule: **normalise only what the annotation guidelines explicitly define as equivalent, and apply it to gold and prediction alike.** Two rules qualified:

| Field | Normalisation | Guideline source |
|---|---|---|
| role_title | A separate gender marker such as `(m/w/d)`, `(w/m/d)`, `(H/F)` or `(all genders)` is removed, including at the end of a longer bracket. Gendered word forms such as `Praktikant/in` stay. | role_title: "Remove a separate gender marker" |
| start | "as soon as possible", "immediately", "ab sofort", "dès que possible" → `asap`. A trailing "or by agreement" / "oder nach Vereinbarung" / "ou à convenir" is dropped. "to be discussed" → empty. | start: the listed normalisations |

I deliberately did **not** normalise anything the guidelines leave open, such as date formats (`1.2.27` vs `1 February 2027`), "per sofort", or a leading "per". `start` remains a textual proxy.

Every run, v1 included, was re-scored with metric version 2. The version is written into every summary and detail CSV, and `extractor.compare` refuses to compare runs that were scored with different versions. The change only affected the fields it was meant to:

| v1 run | role_title (metric 1 → 2) | start (metric 1 → 2) | postings affected |
|---|---|---|---|
| Llama 3.1 | 0.73 → 0.77 | 0.65 → 0.81 | 022 (title); 005, 006, 012, 023 (start) |
| Qwen 2.5 | 0.58 → 0.62 | 0.42 → 0.58 | 022 (title); 005, 006, 012, 023 (start) |

### Title threshold: kept at 0.85

After the gender-marker rule, the v1 title similarities form two clear groups (both models):

- **≥ 0.85:** a short suffix dropped from the same title: 024 `(1393)` 0.868, 005 `(3–6 months)` 0.881, 008 `(100%)` 0.907, 025 `- Zurich` 0.922/0.873, 009 `80-100%` 0.925.
- **≤ 0.74:** words reordered (010 0.52, 016 0.70–0.74), a long part of the title dropped (014 0.71, 018/019 0.69, 020 0.48), or a different title (Qwen 007 "Research Intern" 0.17).

There is no title between 0.74 and 0.868, so any threshold in that range gives identical scores. I kept 0.85 for two reasons. Lowering it to about 0.70 would accept 014 but not 018/019, which are the same error type (a workload/duration suffix dropped), so the cut would be arbitrary. And character similarity cannot separate a harmless reordering (010: 0.52) from a genuinely wrong, truncated title (Qwen 023: 0.43), so no threshold makes reorderings pass without also passing real errors. The threshold was fixed before v2 was run.

## 2. Prompt v2

### What changed and why

v1 embeds the JSON Schema, with short field descriptions from `schema.py`, plus three generic rules. Several of those descriptions are older than the annotation guidelines. The clearest case is `degree_level`, where the description says "'master_only' if only master students" but the guidelines say master_only means *at least master-level studies*, and a completed master's degree counts as `graduate_only`.

v2 (in [src/extractor/prompts.py](../src/extractor/prompts.py)):

1. **Restates the annotation guidelines as instructions**, field by field. Every rule maps to a guideline section:

| v2 rule | Guideline section |
|---|---|
| Requirement = what the candidate must already bring; tasks and preferences are not requirements; the preference word list; qualifiers apply to their own phrase | "Reading a posting" |
| Degree labels describe *who may apply*; completed degree compulsory → graduate_only, including a required master's degree | degree_level table |
| Skills: only named tools; leave out tasks, preferences, examples of a generic requirement, general fields; list every alternative; canonical spellings | required_skills |
| Duration: stated length only, lower bound of a range, years × 12, weeks / 4, null if not stated | duration_months |
| Start: shortest phrase, asap normalisation, drop "by agreement", other events are not start dates | start |
| Language fields: posting language is no evidence; alternatives → plus / false | german_level, english_required |
| Title: copy line 1 exactly, remove only a gender marker | role_title |

2. **Embeds the same JSON Schema without descriptions.** The types, enums and bounds are identical, so the rules are the only explanation of each field and the prompt cannot contradict itself.
3. **No full few-shot postings.** With a 4096-token window the longest posting (001) already needs 2387 tokens under v1, and v2 reaches 3231. A complete example posting would not fit. v2 uses short invented phrases inside the rules instead.

### Keeping v1 reproducible

- The v1 text and the `schema.py` descriptions are unchanged. `tests/test_prompts.py` checks a SHA-256 hash of the full v1 system prompt, and of v2, against the text that produced the cached results.
- I re-ran v1 for both models into a scratch cache. **All 52 extractions were identical to the original cache**, field for field. At temperature 0 these runs are deterministic, so the differences below come from the prompts, not from sampling noise. They are still subject to the small sample of postings.

### Avoiding leakage

- v2 contains no test posting and no text from one. All examples were invented (Looker, Qlik, Java/Kotlin, "March 2028", ...).
- `tests/test_prompts.py` checks that the v2 prompt shares **no five-word sequence** with any of the 26 postings. That check caught a real problem: my first draft used the guideline wording "Bachelor's or Master's student ... or recent graduate", which is nearly verbatim from posting 004, a bachelor_ok example. I rephrased it. The remaining shared four-word phrases are generic ("as soon as possible", the heading "Das bringen Sie mit", "Master's or PhD").
- v2 was written once and run once per model. I did not tune it on the results.

### Is a difference real? Paired changes per posting

For each field: the number of postings that scored higher / lower in the second run (ties left out), with a two-sided exact sign test. With 26 postings, a 2–0 split has p = 0.50 and even 5–0 has p = 0.06. Of the 36 tests, about 2 could reach p < 0.05 by chance alone.

| field | Llama v1 → v2 | Qwen v1 → v2 | Llama v2 → Qwen v2 |
|---|---|---|---|
| company | +0 / −1 (n.s.) | +1 / −0 (n.s.) | +0 / −1 (n.s.) |
| role_title | +3 / −0 (p=0.25, n.s.) | +5 / −0 (p=0.06, n.s.) | +0 / −2 (n.s.) |
| locations | +0 / −15 (p<0.001, **significant**) | +1 / −8 (p=0.04, **significant**) | +9 / −8 (n.s.) |

| workload_max | +2 / −8 (p=0.11, n.s.) | +1 / −0 (n.s.) | +8 / −1 (p=0.04, **significant**) |
| duration_months | +5 / −11 (p=0.21, n.s.) | +4 / −2 (n.s.) | +3 / −2 (n.s.) |

### Conclusion

- **Best run overall: Llama 3.1 with v1.** It has the highest mean field score (0.81) and the most correct field values (254 of 312).
- **v2 did not improve the fields it targeted.** On skills, degree level and duration, every change goes in both directions and none is distinguishable from noise. Qwen's degree macro F1 rose from 0.47 to 0.56, but that is +3 / −5 postings, which is not an improvement.
- **v2 helped where its rule is a pure formatting rule.** Titles improved for both models (+3/−0 and +5/−0). Each is not significant on its own, but the direction is the same for both models. Qwen's start field improved significantly (+7/−0) because it stopped inventing `asap` and stopped taking the publication date.
- **v2 hurt Llama clearly, and both models on locations.** The cause is visible in the outputs. The small models **copy values from the illustrative examples in the instructions**: `"[]"` as a location string (Llama, 9 postings), `workload_min 60` (the example was "60-80%") on 5 postings without a percentage, "Weekly Hours: 40" read as 40% (006, 007, 010), `asap` invented on 8 postings, durations of 24 and 4 from "2 years gives 24" and "4-8 months gives 4", and Qwen listing the canonical-spelling list (`aws, gcp, azure, postgresql, git, c#, spark, react`) as skills for 008, 017 and 023. Qwen also left the header location out on five postings.
- **Model comparison under v2:** Qwen is clearly better than Llama on workload, only because Llama copies values. On every other field the two are indistinguishable.

The lesson: in 7–8B models, aligning a prompt with the annotation guidelines does not pay off automatically. Every concrete example value in an instruction is a candidate output. That matters more than the precision of the rule wording.

### Limitations

- **26 postings, one annotator.** Only large shifts (about 6–0 or 8–1) are detectable. Inter-annotator agreement is unknown, so part of the remaining error is label noise (see the error analysis).
- **Overfitting risk.** The v2 rules come from the guidelines, but I chose *which* rules to stress after seeing v1 errors on the same 26 postings, for example "other events such as the publication date are not start dates" and the duration hint about the title line. There is no separate development set, so a v2 gain would have been optimistic. Given the results, this mainly means the v2 losses should not be read as "guidelines don't help" either.
- **Multiple comparisons.** 36 sign tests at α = 0.05. The locations and workload results are robust (p ≤ 0.004 for Llama), while the start result for Qwen (p = 0.02) is plausible but would not survive a strict correction.
- **Context window.** All runs use Ollama's 4096-token default. The v2 system prompt is about 840 tokens longer than v1. The longest v2 prompt (3231 tokens) still fits with its answer, so nothing was truncated, but a retry adds the previous answer and the error message on top.
- **start is a textual proxy.** Equivalent dates in different formats count as wrong.

### Labels I think are debatable or wrong (not changed)

| posting | field | label | my reading |
|---|---|---|---|
| 024 | german_level | none | "Gute aktive Kenntnisse zweier Amtssprachen": German is one of several acceptable languages, which the guidelines label `plus`. I think the label is wrong. |
| 014 | degree_level | graduate_only | The requirement says "Bachelor's or Master's degree", but the posting is a "University internship" whose salary line addresses "Bachelor … students or graduates". `bachelor_ok` is at least as defensible, and three of the four runs predict it. |
| 014 | english_required | false | "Please apply in English." The guidelines do not cover the application language. Applying in English effectively requires it. |
| 020, 021 | required_skills | empty | "at least one programming language such as R, Python or Stata" / "Python, R, SQL, or similar languages" is treated as a generic requirement with examples, while 001 ("one or more of AWS, Azure or GCP") counts as alternatives. The boundary between an open and a closed list is thin, and all four runs predict the tools. |
| 014, 018, 019, 020 | role_title | full header line | The guideline keeps workload, duration and location suffixes in the title, although they belong to other fields. Every model drops them. The labels follow the guideline, but the guideline may be the thing to change. |
| 013 | duration_months | 6 | Derived from "février à juillet 2027" rather than stated, while the guideline says "record the stated length". |

## 4. Next steps

1. **v3 without copyable values:** describe workload, duration and start rules in words or with obvious placeholders, keep the canonical-spelling table out of the prompt (scoring already maps aliases), and avoid literal `[]`. Test it on new postings, not on these 26.
2. **A development set.** Label 20–30 more postings, tune prompts there, and keep these 26 as a held-out test set.
3. **Ablation:** add one rule group at a time (skills, degree, start) to see which rule helps and which hurts.
4. **Constrained decoding** with Ollama's JSON-schema output to rule out enum and type errors instead of relying on retries.
5. **A second annotator** on a subset to measure agreement, starting with the debatable labels above.
6. A paid model (e.g. GPT-4o-mini) as an upper reference, to separate "prompt problem" from "model size problem".
