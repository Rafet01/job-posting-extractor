# Experiments, phase 2: development set, constrained decoding, prompt v3 and v4

Phase 1 ([experiments.md](experiments.md)) compared two prompts on the same 26 postings that were used to look at errors. Phase 2 fixes that: prompts are developed on a separate **development set** of 26 more postings ([data/dev/](../data/dev/README.md)), and only the final version is scored **once** on the 26 test postings.

All runs: Llama 3.1 8B via Ollama 0.40.17, temperature 0, metric version 2. Tables were generated by `python -m extractor.evaluate` and `python -m extractor.compare`; the full per-language tables are in [outputs/dev/comparison.md](../outputs/dev/comparison.md) and [outputs/comparison_v4.md](../outputs/comparison_v4.md).

## 1. Constrained decoding

**v1-schema** sends the v1 messages but asks Ollama for decoding constrained by the JSON Schema (`response_format: json_schema`), so the model cannot produce an invalid structure.

| dev, n = 26 | v1 | v1-schema | v1-strict |
|---|---|---|---|
| failed extractions | 0 | 1 | 0 |
| retries or cut-offs | 2 | 5 cut-offs | 0 |
| workload_min | 0.92 | 0.35 | 0.88 |
| duration_months | 0.81 | 0.54 | 0.81 |
| start | 0.81 | 0.54 | 0.88 |
| required_skills | 0.49 | 0.42 | 0.49 |

- **v1-schema was clearly worse** (workload +0/−15, duration +0/−7, start +1/−8, all significant). The model left workload, duration and start out of most answers. Those fields have a default in the Pydantic model, so they are *optional* in the JSON Schema, and the grammar allowed the model to close the object without them. In JSON mode the model writes them, because the prompt shows every field.
- It also **kept generating** on one posting until it was stopped. Answers are now capped at 1024 tokens: a cut-off answer is retried and, after three attempts, counts as a failure instead of blocking the run.
- **v1-strict** lists every field as required (null is still allowed). The missing values disappear and the scores match v1, with no retries at all. No difference to v1 is significant.

**Lesson:** constrained decoding guarantees the *shape* of the answer, and follows the schema literally. Anything optional may be skipped. With a strict schema it is as good as JSON mode and removes the retries.

## 2. Prompt v3 and v4 on the development set

**v3** = v1 (schema with field descriptions) plus short rules for the errors v1 made on the dev set: general fields and example lists counted as skills, finished degrees read as `bachelor_ok`, the posting's language taken as a language requirement, shortened titles, missed durations and extra words around start dates. All examples in the prompt are invented, and a test checks that no prompt shares a five-word sequence with a test posting.

**v4** = v3 with the start, german_level, degree_level and example-list rules rewritten after the v3 errors. degree_level became four questions in a fixed order.

| dev, n = 26 | v1 | v3 | v4 |
|---|---|---|---|
| company | 0.92 | 0.92 | 0.92 |
| role_title | 0.73 | 0.85 | 0.88 |
| locations | 0.92 | 0.93 | 0.94 |
| workload_min | 0.92 | 0.88 | 0.77 |
| workload_max | 0.88 | 0.92 | 0.81 |
| duration_months | 0.81 | 0.85 | 0.88 |
| start | 0.81 | **0.46** | 0.85 |
| german_level | 0.61 | 0.48 | 0.59 |
| english_required | 0.81 | 0.92 | 0.77 |
| degree_level | 0.47 | 0.32 | 0.47 |
| is_internship | 0.94 | 0.94 | 0.94 |
| required_skills | 0.49 | **0.62** | **0.64** |
| *mean of fields* | 0.78 | 0.76 | 0.79 |

- **required_skills improved significantly** in both versions (v3 +9/−1, v4 +8/−1 postings).
- **v3's start collapsed** (+3/−12, significant): the rule "write asap for immediately, ab sofort, …" made the model write `asap` for 11 postings without any start date. The phase-1 lesson again: a value named in a rule becomes a default. v4's wording ("null unless the posting names a start") fixed it.
- **degree_level and german_level did not improve with rules.** Errors moved between postings from version to version.

I stopped after v4: apart from skills, every new rule moved errors from one field to another, and more rounds on 26 postings would mostly fit the dev set.

## 3. The one test-set score: v4 against v1

| test, n = 26 | v1 | v4 | paired change |
|---|---|---|---|
| company | 1.00 | 0.96 | +0 / −1 |
| role_title | 0.77 | **0.92** | +5 / −1 |
| locations | 0.99 | 0.95 | +0 / −1 |
| workload_min | 1.00 | 0.92 | +0 / −2 |
| workload_max | 0.92 | 0.92 | +1 / −1 |
| duration_months | 0.81 | 0.65 | +3 / −7 |
| start | 0.81 | 0.88 | +4 / −2 |
| german_level | 0.80 | 0.70 | +0 / −2 |
| english_required | 0.85 | 0.77 | +1 / −3 |
| degree_level | 0.40 | 0.45 | +2 / −0 |
| is_internship | 0.95 | 0.95 | +0 / −0 |
| required_skills | 0.48 | 0.49 | +3 / −6 |
| *mean of fields* | **0.81** | 0.80 | |

**No difference is significant.** The clear gain on the dev set for required_skills (0.49 → 0.64) does **not** carry over to the test set (0.48 → 0.49). v4 writes titles more faithfully and gets the start a bit more often, but loses on duration and the language fields. **v1 remains the best published setup.**

## 4. Why the dev gain did not transfer

- **The dev set is easier in exactly the way the rules target.** The dev postings are paraphrases: they are cleaner than real ads, and requirement phrases such as "like Python, Scala or Java" or "R, SAS oder ähnliche" stand out clearly. Real ads mix tasks, requirements and nice-to-haves in longer, messier text, where the same rule is harder to apply.
- **Rules and dev labels share one reading of the guidelines.** The rules were written while looking at the dev labels, so on dev they agree by construction. The test labels were made earlier, case by case.
- **26 postings per set.** A +8/−1 shift is significant on one set, but the effect of a prompt rule on an 8B model is small compared with the variation between postings.

This is the result the dev/test split exists for: without it, v4 would have been reported as a 0.49 → 0.64 improvement on skills.

## 5. Next steps

1. Split `degree_level` into "required level" and "degree must be finished": rules did not fix it in four prompt versions, so the label design is the more likely problem.
2. Use **v1-strict** as the default request: same quality as v1 on dev, no retries. Score it once on the test set.
3. Try a larger or paid model as a reference, to see how much of the remaining error is model size rather than prompt wording.
4. Collect real (not paraphrased) dev postings, so the dev set has the same messiness as the test set.
